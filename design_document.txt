Design notes: facility database and ID hash table
Asanga Rimal

Hash function
Every facility ID is trimmed and changed to uppercase before it is checked,
hashed, stored, or compared. A typed id like f004 becomes F004 first.
The table does not call a library hash.

Capacity is the named constant INITIAL_CAPACITY in HashTable.h. It is 11.
That number is the bucket count, not a limit on how many facilities we can store.

For an uppercase key:

    hash = 0
    for each character c in the key:
        hash = (hash * 31 + ASCII value of c) mod capacity

The index is that remainder. 31 is a small odd multiplier, so IDs that only
differ in the last digit do not all fall into one bucket. The remainder is
what keeps the index inside 0 .. capacity-1.

With this function, F009 and F010 both land in bucket 0, so the sample file
produces one collision. F001, F013, and F025 all land in bucket 3. Those three
are in testdata/collision so we can show a longer chain.

Collision strategy
Separate chaining. Each bucket is the head of a linked list of nodes, and
each node holds one facility. I used chaining because the project does not
want a fixed maximum number of facilities. A chain can grow. Open addressing
would eventually fill the array and force us to reject a good record.
We do not resize. A full table cannot happen with this design, so there is
no "table full" warning.

New nodes are inserted at the front of the chain. That only affects the
list inside the bucket. The screen list follows facilities.txt, from a
vector that we push onto when a record is accepted. ID search does not walk
that vector. It hashes the ID and walks that one chain.

What counts as a collision
One collision means one accepted insert into a bucket that already had at
least one node. Stepping through the chain does not add more to the count.
If the ID is already in the table, insert returns false before the count
changes. So a later f001, after F001 was stored, is a rejected duplicate
and the collision total stays the same. Rejected lines (bad format, unknown
building, and so on) never reach insert.

Facility records
Facility stores the uppercase ID, the facility name, the building, and the
category. The building saved on the record is the spelling from buildings.txt,
even if facilities.txt used different capitalization. The facility name and
the category keep the spelling from the accepted line, including internal
spaces. A later line with the same ID does not replace the first record,
even when the names differ.

Load checks, in this order: number of fields, empty fields, ID format
(F and exactly three digits), unknown building, duplicate ID. Blank lines
and comment lines are skipped. A comment is a line whose first non-space
character is #. A # later in the line, as in Room #5, is normal text.
Trim removes spaces, tabs, and the carriage return, so a Windows file loads.

ID search has three results. An ID that is not F plus three digits is an
invalid format. A valid ID that misses the table is not found, and the
message shows the uppercase ID. A hit prints the stored record.

Other modules
Sebastian is adding the campus graph. Anugrah is adding the department tree.
This branch does not implement those. main loads buildings.txt, then
facilities.txt, and leaves marked spots for the other two files so the
load order can stay buildings, connections, facilities, departments.

Design notes: campus graph and BFS
Sebastian

Graph representation
The graph is an adjacency list inside the CampusGraph class. There is a vector
of building names and a vector of vectors of ints. adjList[i] holds the
indexes of the buildings that touch building i. I chose an adjacency list
because it grows with the data, so there is no fixed size and no wasted space
for a campus with few walkways. A matrix would need n by n cells even when
most are empty. Checking whether two buildings are already connected means
looking through one short list, which is fine for a campus.

Buildings stay in the order of buildings.txt. Neighbors stay in the order
the connections were accepted. I never sort them, because sorting could
change the BFS order.

Loading connections
main loads buildings.txt first and gives the accepted names to the graph with
setBuildings. Then loadConnections reads connections.txt with getline. Blank
lines and lines whose first non-space character is # are skipped. Checks, in
this order: number of fields (must be 2), empty fields, unknown building on
either side, a building connected to itself, and a duplicate. Building names
are matched ignoring case and with outer whitespace trimmed, so the graph
always shows the spelling from buildings.txt. A reversed duplicate (B|A after
A|B) is caught because the duplicate check looks for the edge from either end.
Every rejected line prints the file name, line number, and reason, and then
loading continues. A missing file prints an error and the graph stays empty.

An accepted connection is added to both buildings, but the connection count
goes up only once. Total connections is that count, so it is never doubled.
The degree of a building is the size of its neighbor list.

Display
View graph prints each building and its neighbors, or (no connections) when
the list is empty. Counts and degrees prints total buildings, total
connections, and the degree of every building. If there are no buildings,
both print a clear message and the totals show 0.

BFS reachability
The menu asks for a starting building. A blank name is an error in main. An
unknown name prints an error and returns to the menu. BFS uses a std::queue
and a vector<bool> visited. I mark a building as visited when I put it in the
queue, not when I take it out, so no building is queued twice. A second vector
keeps the distance in connections, which is the distance of the building it
was reached from plus one. Buildings print in the order they leave the queue,
each with its distance, and then "Reachable: X of Y buildings". The start is
at distance 0 and counts as reachable, so an isolated building reaches only
itself. Buildings in other connected components are never reached.

Same graph for later features
Display, counts, and BFS all use the same adjList. The Final shortest path and
the connectivity report can reuse it too.
